Two older v33 statements are superseded by the explicit update prompt and the later Goal sections:

- Goals is a dedicated `/goals` primary workspace on desktop and mobile. It is not a Plan tab. Plan remains the independent calendar.
- A normal overall-goal update uses a 5%-increment slider and a required short note. Milestone updates remain separate inline actions. The system stores both employee-reported overall progress and milestone-derived weighted progress and shows any difference instead of silently reconciling it.

These are reversible product interpretations supported by the latest, most specific approved material. No security, retention, or irreversible external decision was assumed.

## Repository baseline

The existing application has no Goal table, Goal RLS helper, Goal transaction, Goal read model, `/goals` route, Goal navigation item, Goal email section, Goal fixture, or Goal test. The affected implementation is therefore a new vertical slice that reuses the existing application shell and infrastructure rather than a rewrite of unrelated work-management modules.

Existing reusable authorities:

- signed-in Server Component reads through the request-scoped Supabase client;
- PostgreSQL RLS as the view/edit authority;
- security-definer RPCs with row locks, optimistic versions, idempotency, audit, and notifications;
- private `task-attachments` Storage bucket and server-authorised signed downloads;
- shared `SideDrawer`, `Modal`, `AttachmentPicker`, status, progress, whole-row interaction, motion, dark-theme, and responsive primitives;
- local Auth fixtures, pgTAP, real-stack integration tests, Playwright/Axe, generated database types, and the 14-gate verification runner.

## Planned database objects

The exact SQL names below are intentionally explicit so schema, types, documentation, and tests use one vocabulary.

- Enums: `goal_status`, `goal_health`, `goal_version_status`, `goal_update_kind`, plus Goal audit and notification values.
- Tables: `goals`, `goal_participants`, `goal_versions`, `goal_milestones`, `goal_agreements`, `goal_updates`, `goal_milestone_updates`, `goal_attachments`, `goal_work_links`, `goal_support_requests`.
- Audit/notification extensions: nullable `goal_id` subjects with indexes and foreign keys.
- Helpers: `can_view_goal`, `can_update_goal`, `can_edit_goal_structure`, `can_agree_goal`, weighted-progress and attention predicates, Goal storage-path resolution.
- Transactions: Goal setup/draft, quick update, milestone update/complete, structural proposal, structural agreement, work linking, support acknowledgement/resolution, and authorised attachment view.
- Read models: compact Goal overview, Goal attention signals, and team Goal summary, all `security_invoker`.

## Migration and preservation strategy

1. Add a forward-only v33 Goal migration chain after the existing application migrations: enum/audit vocabulary, schema, security/RLS, operations, views, and additive `create or replace` repairs found by real-stack verification.
2. Use nullable Goal foreign keys when extending generic audit/notification records so all current rows remain valid.
3. Reuse the private bucket with a distinct `goals/<goal_id>/...` path namespace and policies that delegate to Goal helpers.
4. Preserve every current task, routine, attachment, audit, user, visibility, settings and email record.
5. Regenerate TypeScript database types only after a full local reset proves the migration and seed from zero.
6. Keep unrelated routes and task transactions unchanged except where navigation, My Day, global audit/attachment reading, or weekly-summary composition must consume Goal data.
